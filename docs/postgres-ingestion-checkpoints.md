# Fenced PostgreSQL ingestion checkpoints

Apply the opt-in migrations through `004_ingestion_checkpoints.sql` before using the fenced store. The migration adds a nullable `checkpoint jsonb` column; existing jobs retain `NULL`. The fenced store requires a pg-compatible `pool.connect()` with transaction-capable clients; query-only pools fail closed.

For the explicit fenced service mode, also apply additive `005_ingestion_service_protocol.sql`, drain every running legacy lease, and call the administrative `enableFencedIngestionService(pool)` separately. This action persists the protocol under an exclusive writer barrier and rejects any running lease; startup never calls it. Configure `MATH_UNIVERSE_INGESTION_MODE=fenced`. Startup checks the persisted protocol, then wires the token-fenced store. The legacy service default and legacy store API remain available before activation and retain their old unfenced semantics. After activation, database triggers reject legacy claim/renew/complete/fail, DELETE and TRUNCATE. The legacy producer's enqueue/dedup remains usable, including existing running/completed jobs. No Book backend or gate changes occur.

Protocol activation requires a trusted schema owner/migration role; runtime roles must not own tables/functions or receive modification rights on the protocol table. Workers need schema usage, job SELECT/INSERT/UPDATE and sequence usage, plus the public read-only status function. The per-transaction claim capability protects supported APIs against accidental old-writer coexistence; it does not authenticate SQL callers who can read claim tokens or defeat a privileged database owner. Keep legacy processes stopped; the barrier proves their writes are rejected, not that their processes have exited.

`createFencedIngestionJobStore(pool).checkpoint({jobId, workerId, claimToken, checkpoint})` replaces a checkpoint only when the job is running, its worker and claim token match, and its lease is still strictly later than the database transaction's `now()`. A stale token, wrong owner, or expired lease produces the same rejection as `renew`. Saving a checkpoint does not extend the lease. Retry and expiry recovery preserve it for the next claim; the worker must independently verify its contents before resuming.

Checkpoint input must be a plain JSON object. Validation rejects accessors, serialization hooks, cycles, sparse arrays, unsupported values and exotic prototypes before querying PostgreSQL. The serialized UTF-8 JSON limit is 256 KiB, with at most 20,000 visited values and 24 nesting levels. This validates inert data, not the application's checkpoint schema. Checkpoints may contain private document data and require the queue's access and retention controls.

`claim({workerId, leaseSeconds, jobId})` optionally targets one positive safe integer ID. Without `jobId`, selection retains queue order and `SKIP LOCKED` behavior. A running lease expires at `lease_until <= now()`. In the same statement, expired running jobs with exhausted attempts become failed and have their owner, token and lease cleared; an explicit `jobId` also scopes this maintenance to that job. Claim returns `worker_id` and `checkpoint`. PostgreSQL bigint job IDs are returned as JavaScript safe integers; larger IDs are unsupported and rejected.

The migration runner reads and hashes every raw UTF-8 script on every invocation, validates a strict checksummed prefix, and holds its advisory lock and unapplied scripts in one READ COMMITTED transaction. Populated filename-only histories are rejected as `MATH_MIGRATION_HISTORY_UNVERIFIED`; current file hashes cannot establish historical execution. Empty legacy ledgers can bootstrap. No automatic adoption of nonempty histories is provided. It strips script-level transaction wrappers while preserving function bodies. Nothing invokes migrations or starts ingestion automatically.

## PostgreSQL lock waits and lease expiry (F01)

For the corrected fenced service contract apply additive `006_ingestion_lease_clock.sql` through the strict checksummed generic migration runner. SQL001–005 and Book SQL001–005 are historical bytes and remain unchanged. SQL006 waits for the exclusive protocol barrier before replacing the guard; both existing legacy and fenced modes remain unchanged. It neither activates the protocol nor grants runtime roles new privileges.

The fenced store acquires the protocol advisory lock and, for renew/checkpoint/complete/fail, locks the target job row before evaluating ownership against PostgreSQL `clock_timestamp()`. Claim retains `FOR UPDATE SKIP LOCKED`; lease assignment uses wall time after candidate locking. The SQL006 row guard samples wall time after its protocol row lock, rejects expired ownership even if a caller's statement predicate was evaluated before a wait, and requires a newly acquired/renewed deadline to be strictly later than its check. Expiration uses the strict boundary: `lease_until <= checked_at` loses ownership. The trigger's dedicated expiry SQLSTATE `MU001` maps to the existing public `JOB_LEASE_LOST`; unrelated database failures still propagate.

The operation linearizes at its post-lock ownership check. Database commit, network delivery or event-loop scheduling can occur later, so a returned lease snapshot is not a guarantee of ownership at arbitrary subsequent wall time. Database wall time must be suitably synchronized; this correction is not a monotonic-clock or host-clock-jump solution.

The standalone fenced API remains compatible with SQL004-only installations and legacy mode; neither startup nor the store applies migrations or activates protocol mode. A SQL005-only database still has its earlier transaction-clock trigger: updating the store improves its own checks but does not qualify direct SQL/old-writer expiry protection. SQL006 plus the corrected store is the reviewed combination. Default legacy service behavior remains deliberately unfenced.

The checksummed runner continues to hash raw UTF-8 working-file bytes and fail closed on source drift or unverified filename-only history. SQL006 does not normalize SQL, adopt current hashes into historical ledgers, repair EOL mismatches, or supply an immutable dependency artifact. See the F01 remediation report for F03/R06 carry-forward limits.
